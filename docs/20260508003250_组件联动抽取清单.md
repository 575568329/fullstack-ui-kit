# fullstack-ui-kit 组件联动抽取清单

## 1. 目的

这个清单用于联动两个项目：

- `D:\Study\fullstack-ui-kit`
- `D:\Study\rag-docs-assistant`

目标不是把两个项目混在一起，而是把 `rag-docs-assistant` 里稳定、可复用、可讲面试的 UI 抽成组件库，再由业务项目做数据适配。

## 2. 抽取原则

1. 组件库只保留展示层，不承载业务请求和协议解析。
2. 业务项目负责类型适配和数据转换。
3. 优先抽取 AI 场景、RAG 场景、异步状态、前端疑难杂症四类组件。
4. 一个组件如果只在单页单场景中出现，不优先抽取。
5. 能讲清楚“为什么要抽象”的组件优先。

## 6. 在 `rag-docs-assistant` 中的适配方式

### 6.1 类型适配

业务项目保留自己的领域类型，例如：

- `ConversationMessage`
- `SourceRef`
- `KnowledgeBase`
- `Document`

然后在业务层做映射，例如：

- `ConversationMessage -> ChatMessageItem`
- `SourceRef[] -> SourceGroupPanelProps / CitationListProps`
- `SourceRef -> SourceCardItem`
- `KnowledgeBase -> KnowledgeBaseCardProps`
- `Document -> DocumentPreviewCardProps`

来源引用不能只做单条来源卡。`rag-docs-assistant` 当前的来源展示会按文件聚合、折叠展开、保留最高分并支持下载入口，因此组件库里应优先抽 `SourceGroupPanel` 或 `CitationList` 这种来源汇总组件，`SourceCard` 只作为单条来源展示单元。

### 6.2 数据适配

业务项目只负责把后端返回的数据整理成组件库能理解的展示数据，不把协议处理塞进组件本体。

### 6.3 页面接入顺序

1. 先接 `src/components/chat/ChatPage.tsx`
2. 再接来源引用区
3. 再接状态反馈区
4. 再接知识库、文档和流程卡片
5. 最后接实体和图谱链路

## 8. 验收标准

1. 组件库里的组件足够纯，不依赖 `rag-docs-assistant` 的业务内部实现。
2. `rag-docs-assistant` 能通过适配层直接接入组件库。
3. 对话、来源、状态、流程四条链路都能讲清楚。
4. 组件说明和示例能支持面试表达。
5. 后续扩展时不会把组件库重新做成业务项目。

## 9. 备注

- 当前清单优先服务“组件库沉淀 + 业务项目复用”这条主线。

## 10. 执行计划

### 阶段 1：先定接口和边界

- 冻结 `ChatMessage`、`StreamingText`、`SourceCard`、`CitationList`、`SourceGroupPanel` 的公开 props。
- 明确组件库只负责展示层，业务项目只负责数据适配。
- 把 `rag-docs-assistant` 里的 `ConversationMessage`、`SourceRef`、`KnowledgeBase`、`Document`、实体节点与组件 props 的映射关系写清楚。

### 阶段 2：先做对话和引用链路

- 先在组件库里补 `StreamingText`、`CitationList`、`ThinkingIndicator`。
- 再补 `ChatMessage` 的统一版本，保证对话展示和流式展示能连起来。
- 在 `rag-docs-assistant` 里优先改 `src/components/chat/ChatPage.tsx`，让真实聊天入口接入新组件。
- 来源引用优先按 `SourceGroupPanel` 抽象，保留按文件聚合、折叠展开、最高分展示和下载入口。

### 阶段 3：补状态和错误恢复链路

- 实现 `AsyncStateView`、`ErrorStatePanel`、`RetryNotice`。
- 统一知识库加载、检索失败、文档处理失败等状态展示。
- 让业务项目中的加载、失败、重试行为都走同一套壳。

### 阶段 4：补知识库、文档和上传链路

- 先实现 `KnowledgeBaseCard`、`FileStatusList`、`FileDropZone`。
- 再评估是否需要把三者组合成更高层的 `UploadPanel`。
- 补 `ConversationHistoryPanel`、`DocumentPreviewCard`、`StepTimeline`、`PromptComposer`。
- 让文档导入、检索、生成、会话管理这些真实业务页面能逐步替换到组件库。

### 阶段 5：补实体、图谱和调试组件

- 视业务需要补 `ToolCallPanel`、`ActionTrace`、`ExecutionLogPanel`、`SseStreamViewer`。
- 把 `EntityTags`、`GraphSearchBox`、`NodeDetailPanel`、`GraphCanvasShell` 纳入适配后抽取范围。
- 这条链路用于支撑“答案 -> 实体 -> 图谱”的面试讲解。
- 这些组件优先服务“可讲清楚”和“可排查问题”两个目标。

### 阶段 6：验证与收口

- 每个组件补一个最小示例页。
- 在 `fullstack-ui-kit` 里验证展示效果。
- 在 `rag-docs-assistant` 里验证是否能通过适配层接入。
- 发现职责重叠时，优先收缩组件能力，而不是继续扩 API。

## 11. Claude Code 执行方式

### 11.1 分工

- Claude Code：负责按任务单实现代码、补示例、跑验证、回传结果。
- Codex 主线程：负责拆任务、定义边界、审阅结果、指出问题、决定是否通过。

### 11.2 执行粒度

一次只交给 Claude Code 一个明确子任务，不把整份计划一次性丢过去。

推荐粒度：

- 一个组件实现
- 一个适配层接入
- 一个文档组件联调
- 一个页面替换任务

不推荐粒度：

- 第一批全部组件一起做
- 同时改组件库和业务项目多个页面
- 一次性重构整个聊天链路

### 11.3 单个任务的固定结构

每次派工都写成任务单，至少包含：

1. 目标
2. 文件范围
3. 不允许修改的边界
4. props / 类型要求
5. 示例页要求
6. 验证命令
7. 回传格式

### 11.4 审阅标准

我每轮只按这几个标准审：

1. 是否符合当前任务边界
2. 是否复用了现有模式，没有乱起抽象
3. 是否把业务逻辑错误地塞进组件库
4. 组件 props 是否足够稳定
5. 示例页是否能说明用途
6. 类型检查和构建验证是否通过
7. 接入 `rag-docs-assistant` 后是否真的解决了目标场景

### 11.5 打回规则

出现下面情况就直接打回 Claude Code 继续改：

- 功能达到一半，只做了展示没做接入
- 超出任务边界顺手改其他模块
- props 设计失真，和业务实际对不上
- 组件库耦合了 `rag-docs-assistant` 业务类型
- 没有验证或验证结果不完整
- 示例页看不出组件价值

### 11.6 每轮输出要求

Claude Code 每次完成后必须回传：

- 改了哪些文件
- 完成了哪些功能
- 没完成什么
- 跑了哪些验证
- 有哪些风险或后续项

我收到后只做两件事：

- 审阅是否达到效果
- 不达标就继续给出明确修改指令让它重做
